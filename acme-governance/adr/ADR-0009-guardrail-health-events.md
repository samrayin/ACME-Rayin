## 1. The problem, verified not assumed

When the gateway guardrail hook is switched on in `record` mode, CAIRO will show
**what the guardrails would have caught** and will not show **how often the
guardrail was reachable, or what it cost**.

Verified by reading the code rather than inferring:

- `rayin-guardrails/app/events.py` opens *"Emits a decision event for every
  `/v1/guard` call"* and pushes each durably to CAIRO's Postgres. So allows,
  redacts and would-blocks **do** reach the Guardrails page. The detection half
  is covered.
- The reliability half cannot be, **by construction**. When the hook's call
  times out, is refused, or fails to authenticate, `rayin-guardrails` never
  receives the request. There is no decision to emit and nothing to push. An
  absent event leaves no trace — the count cannot be reconstructed later from
  anything CAIRO holds.
- Round-trip duration is measured on neither side. ADR-0005 §5 Step 1 names
  "p50/p95 added latency" as a deliverable of exactly this step; ADR-0005 F5
  records that a p95 was *not definable* against the pre-fix judge spread, and
  nothing has replaced it since.
- **No metrics substrate exists.** There is no `prom-client`, no `/metrics`
  endpoint, no Prometheus and no Alertmanager anywhere in this repository. The
  `metrics` hits under `web/src/features/metrics/` are Langfuse's product
  analytics for customer traces — unrelated to operational monitoring.

The practical consequence: CHG-2026-038 chose a 2s timeout on the argument that
1s would truncate the slow tail where `would_block` lives. **That argument is
currently unfalsifiable.** The number that would confirm or refute it —
`guard_unavailable` at 2s — is the exact number nothing records.

## 2. Scope

**In:** a dedicated table for guardrail *health* (as distinct from guardrail
*decisions*), the ingest path that fills it, the credential that authorises it,
the definitions of ADR-0005 §3d's three metrics against it, and an honest
statement of what building this actually costs.

**Out:** alerting infrastructure (§4.3 — none exists and this ADR does not
create it); ADR-0005 F2's guardrails-side inner timeout; enforce mode; any
change to guardrail decision semantics; the stdout bridge (CHG-2026-041), which
this supersedes but does not remove until this ships.

## 3. Decision — a dedicated table, not a widened enum

### 3.1 Why a separate table at all

A `guard_unavailable` is **not a guardrail decision**. It is the absence of one.
Widening `AcmeGuardrailEventAction` to carry it would make the decision table
assert something it does not mean: every existing query, every page, the tiered
content rules (`allow` = metadata only, `redact` = redacted text, `block` = raw
content encrypted) and the dedup key all assume a decision was actually reached.
A row saying "no decision was reached" inside that table is a category error
that every future reader would have to special-case.

The two also differ in every operational dimension that matters: retention,
volume, sensitivity (health rows carry no prompt content at all), and who reads
them. Separate table.

### 3.2 The table

Prisma model `AcmeGuardrailHealthEvent`, mapped to `acme_guardrail_health_events`.

| Column | Type | Notes |
|---|---|---|
| `id` | `String @id @default(cuid())` | House convention. |
| `eventId` | `String @unique` | Idempotency key, generated by the hook. Same role `eventId` plays on the decision table, so a retried push is a no-op rather than a duplicate. |
| `projectId` | `String` | Scoping. Indexed with `occurredAt`. |
| `occurredAt` | `DateTime` | When the hook ran — the hook's clock. |
| `receivedAt` | `DateTime @default(now())` | When CAIRO stored it. Two clocks kept separately; a gap between them is itself a signal (buffered pushes catching up after an outage). |
| `guardrailName` | `String` | `cairo-guardrail` today. Present so a second guardrail (ADR-0005 F7 proposes splitting PII and jailbreak) does not need a migration. |
| `mode` | `AcmeGuardrailHealthMode` | `RECORD` \| `ENFORCE`. A latency figure means something different in each; mixing them silently would corrupt the percentiles. |
| `outcome` | `AcmeGuardrailHealthOutcome` | See 3.3. |
| `called` | `Boolean` | Whether a call to `/v1/guard` was actually made. Keeps exclusions out of availability and latency figures without the reader inferring it from a null. |
| `durationMs` | `Int?` | Round-trip, **null when `called` is false**. Null ≠ 0: zero would assert an instantaneous call that never happened. |
| `failureClass` | `AcmeGuardrailFailureClass?` | Null unless the call failed. See 3.4 — this is the "event type" the design brief asked for. |
| `httpStatus` | `Int?` | Populated only for `HTTP_ERROR`, so a 503 is distinguishable from a 401 without parsing prose. |
| `litellmCallId` | `String?` | **The correlation field.** Indexed. |
| `agentId` | `String?` | Which application key. From proxy-injected authenticated metadata only, never caller-supplied — same rule the decision path already follows, because a forgeable value poisons the evidence. |
| `direction` | `AcmeGuardrailEventDirection` | **Reused, read-only.** See §7. |

Indexes: `@@index([projectId, occurredAt])`, `@@index([occurredAt])`,
`@@index([litellmCallId])`, `@@unique([eventId])`.

### 3.3 `outcome` — a new enum, not the decision enum

```
enum AcmeGuardrailHealthOutcome {
  ALLOW              @map("allow")
  WOULD_BLOCK        @map("would_block")
  WOULD_REDACT       @map("would_redact")
  BLOCKED            @map("blocked")
  REDACTED           @map("redacted")
  GUARD_UNAVAILABLE  @map("guard_unavailable")
  GUARD_UNREADABLE   @map("guard_unreadable")
  EXCLUDED           @map("excluded")
}
```

These are the hook's own outcomes, already implemented and tested in
CHG-2026-014/041. `EXCLUDED` matters more than it looks: ADR-0005-A layer 3 has
to verify **live** that the Step 0 judge exclusion fires for the judge key and
for nothing else. Without a record, "correctly excluded" and "the hook never ran"
are indistinguishable from outside — and those have opposite meanings for
whether the loop prevention works.

### 3.4 `failureClass` — the event type the brief asked for

```
enum AcmeGuardrailFailureClass {
  TIMEOUT        @map("timeout")        // the 2s cap fired
  HTTP_ERROR     @map("http_error")     // non-200; see httpStatus
  AUTH_FAILURE   @map("auth_failure")   // 401/403, or the shared secret absent
  TRANSPORT      @map("transport")      // refused, DNS, reset — never reached the service
  UNPARSEABLE    @map("unparseable")    // answered, but not a verdict we could read
  CLIENT_MISSING @map("client_missing") // httpx absent from the image
  OTHER          @map("other")
}
```

**Why this is separate from `outcome` rather than folded into it.** The hook's
`decide()` deliberately collapses every failure to one behaviour — "I do not
know what the guardrails think" — because the *response* must not depend on
*why*. Diagnosis does depend on why. `AUTH_FAILURE` means a misconfigured
credential and someone must act now; `TIMEOUT` means the judge is slow and the
2s cap is doing its job. Both are `GUARD_UNAVAILABLE` to the request, and they
are not the same incident. Two fields, one for behaviour and one for cause.

### 3.5 Retention — the part that needs saying out loud

This table takes **one row per gateway request**. That is the same order of
volume as `AcmeLitellmRequestLog`, and it lands in a store with **no deletion
path at all (P0-11, open, P0)**. The 30-day retention job (PR #51) is written,
unmerged, and gated behind the least-privilege cutover (ADR-0004) because it
deletes from the append-only evidence table.

So this design **adds unbounded growth to a system that cannot currently purge
anything**. That is not a reason to abandon it — the data is needed — but it is
a precondition to state rather than discover: either this table is added to the
retention job's scope before it ships, or it ships knowing it grows without
bound. Health rows carry **no prompt content**, which makes them far safer to
purge aggressively than decision rows; a shorter retention (7–14 days) is
defensible here and is not for the decision table.

## 4. The three §3d metrics

### 4.1 Where they come from: derived from the table, not emitted

ADR-0005 §3d names `guardrail_calls_total{outcome}`, `guardrail_latency_seconds`
and `guardrail_unavailable_total` in Prometheus's idiom. **There is no
Prometheus here, and no `/metrics` endpoint on anything ACME owns.** Emitting
real metrics would require: a metrics library in the gateway image, an exporter
endpoint, a Prometheus instance, scrape configuration, and storage — none of
which exist, all of which are their own infrastructure change.

**Decision: derive all three from the table by query.** The table is the source
of truth; the metrics are views over it. This adds no infrastructure, and the
figures are exact rather than sampled. The cost is that they are pull-only —
there is no push-based alerting (§4.3).

### 4.2 The definitions

```sql
-- guardrail_calls_total{outcome}
SELECT outcome, count(*) AS total
FROM acme_guardrail_health_events
WHERE project_id = $1 AND occurred_at >= $2
GROUP BY outcome;

-- guardrail_latency_seconds  (p50 / p95 — ADR-0005 §5 Step 1's deliverable)
SELECT percentile_cont(0.50) WITHIN GROUP (ORDER BY duration_ms) / 1000.0 AS p50,
       percentile_cont(0.95) WITHIN GROUP (ORDER BY duration_ms) / 1000.0 AS p95
FROM acme_guardrail_health_events
WHERE project_id = $1 AND occurred_at >= $2 AND called AND duration_ms IS NOT NULL;

-- guardrail_unavailable_total  (+ the breakdown that makes it actionable)
SELECT failure_class, count(*) AS total
FROM acme_guardrail_health_events
WHERE project_id = $1 AND occurred_at >= $2 AND outcome = 'guard_unavailable'
GROUP BY failure_class;
```

`called AND duration_ms IS NOT NULL` in the latency query is load-bearing:
including exclusions would divide by a denominator containing calls that never
happened, and understate p95 by exactly the requests that cost nothing.

### 4.3 How an operator actually uses these — and the honest gap

**Querying:** through a read-only console view (§5.3), behind the existing
Security Analyst role, which is already deny-by-default and already the role
that reads guardrail evidence.

**Alerting: does not exist, and this ADR does not create it.** There is no
Alertmanager, no scheduled evaluator, and no notification path. Saying
"`guardrail_unavailable_total` alerts at X" would be describing a system that
is not there. Three honest options, none in this scope:

1. A worker job evaluating thresholds on a schedule and writing a finding —
   smallest, reuses the existing worker.
2. Export to the customer's own monitoring — already Horizon 1 on the roadmap
   ("export to the customer's security monitoring"), and the right long-term
   answer for a customer-operated deployment.
3. Real Prometheus. Largest; buys little that (1) does not, for one cluster.

**Until one of those exists, this capability produces evidence that is looked
at, not evidence that shouts.** That distinction should be explicit to anyone
reading a readiness claim about it.

## 5. Credential, endpoint, console, release

### 5.1 The credential, and the limitation that cannot be designed away

The gateway must authenticate to CAIRO's public API. The existing pattern is a
**CAIRO project API key** (public + secret), exactly as `rayin-guardrails`
already uses for its own push (`RAYIN_PUSH_PUBLIC_KEY` / secret).

**Provisioned through the console, not a raw API call** — project settings →
API keys (`web/src/features/public-api/components/ApiKeyList.tsx`), which is
behind the `apiKeys:CUD` permission and records a `note`. Required `note`:
`gateway-guardrail-health-push`. Same discipline as every key provisioned this
week; the raw-API route is what CHG-2026-029 demonstrated as an audit-trail
bypass, and it is not used here.

Gateway environment variables, added to the `litellm-provider-keys` Secret:

| Variable | Purpose |
|---|---|
| `CAIRO_HEALTH_PUSH_URL` | In-cluster service DNS for CAIRO web. Never the public ingress. |
| `CAIRO_HEALTH_PUSH_PUBLIC_KEY` | Public half. |
| `CAIRO_HEALTH_PUSH_SECRET_KEY` | Secret half. |

**How narrowly can it be scoped? Not as narrowly as it should be, and this is
a real finding, not a caveat.** Checked directly:

- `ApiKeyScope` is `ORGANIZATION | PROJECT` — nothing finer.
- `ApiAccessLevel` is `"organization" | "project" | "scores"`. Only one
  narrower-than-project level exists, and it is for scores.

So **a project-scoped key can call every project-scoped public API route.** A
key issued for pushing health events can also ingest traces, push guardrail
decisions, and anything else at project level. There is no per-endpoint scope
to grant.

What is achievable today, and should all be done:

1. **A dedicated key**, not a shared one — in particular **not** the
   `rayin-guardrails` push key. Two consumers, two credentials, two blast
   radii, independently revocable.
2. **`expiresAt` set**, so an unrotated credential expires rather than living
   forever.
3. **The `note` above**, so it is identifiable in the console without guesswork.
4. **Project-scoped, never organization-scoped.**

What would actually close it: a narrower `ApiAccessLevel` (e.g.
`guardrail-health`) restricting the key to this one route. That is a change to
the authentication model, affects every consumer of `RouteAccessLevel`, and is
**larger than this ADR** — named here as a follow-on rather than smuggled in.

**Owner-accepted as a named follow-on, 2026-09-23, and tracked as issue #115**
so the limitation is not later mistaken for an oversight. It is a pre-existing
property of the auth model — the `rayin-guardrails` push credential already has
it — surfaced by this ADR rather than introduced by it. For a customer-operated
deployment, "this key can only do one thing" is a claim a regulated buyer is
likely to ask about directly; today the honest answer is that key scope is
project-wide, and that answer should be given knowingly rather than discovered
during a review.
Until then, the honest statement for a readiness review is: *this credential is
project-scoped and cannot be scoped tighter with the current auth model.*

### 5.2 The endpoint

`POST /api/public/guardrail-health-events`, built with
`createAuthedProjectAPIRoute` (action `guardrailHealthEvents:create`), mirroring
`web/src/pages/api/public/guardrails-events.ts`. A Zod body schema whose enums
match §3.3/§3.4 exactly, and an ingest service alongside
`acmeGuardrailsEventsIngestService.ts`, upserting on `eventId` so retries are
idempotent.

Accepts a **batch**, unlike the decision endpoint. One row per gateway request
at one HTTP call each would make CAIRO's availability a factor in gateway
throughput — which is precisely the coupling this capability exists to measure,
not to create.

### 5.3 Console

A read-only **Guardrail health** view behind the Security Analyst role: the
three §4.2 figures over a selectable window, the `failureClass` breakdown, and a
recent-events table filterable by outcome and agent. No mutation surface —
nothing here is editable, so no write path and no new permission beyond read.

It does **not** extend the existing Guardrails page. Decisions and health are
different questions asked by different people at different times; merging them
invites exactly the conflation §3.1 rejects.

### 5.4 The push must not be in the request path

**The hook's push to CAIRO must be detached and buffered** — a background task
with a bounded queue, dropping oldest under pressure, never awaited inside
`apply_guardrail`. The guard call itself is synchronous by design (CHG-2026-038)
because its verdict is needed. The health push has no such claim on the request:
if it were synchronous, this capability would add latency to the request in
order to measure the latency of the request. `rayin-guardrails`'
`schedule_push` is the existing precedent and the right shape.

A dropped health row is acceptable and must be visibly acceptable: the buffer's
own drop count is itself worth recording, or the gap is silent.

### 5.5 Release

One **web image release** (`acme-v4.38.0.N`) carrying the migration, endpoint
and console view; the migration runs on web start-up as all others do. Worker is
untouched. Separately, a **gateway ConfigMap apply plus restart** for the hook's
push path, and the Secret change for the credential. **Three owner-gated steps,
sequenced: credential → web release → gateway restart.** A gateway pushing to an
endpoint that does not exist yet fails closed into its buffer, which is safe but
pointless; the reverse order wastes a restart.

## 7. Explicit confirmation: nothing existing is altered

Stated as the design brief requires, and checked rather than asserted:

- **`AcmeGuardrailEventAction` is not altered.** No value added, removed or
  renamed. It keeps exactly `ALLOW`, `REDACT`, `BLOCK`.
- **`acme_guardrail_events` is not altered** — no column added, no index
  changed, no constraint touched.
- **No existing query against either is affected.** This design adds a table; it
  does not read from, write to, or change the shape of the decision path.
  `web/src/pages/api/public/guardrails-events.ts`, its
  `z.enum(["allow","redact","block"])`, and `acmeGuardrailsEventsIngestService.ts`
  are untouched.
- **One deliberate reuse, read-only:** `AcmeGuardrailEventDirection`
  (`input`/`output`). The new table references it; **no value is added to it by
  this change.** Reuse is not alteration. The alternative — a duplicate
  direction enum — was rejected as two enums that must be kept in step for no
  benefit. If health events ever need a direction decisions do not have, that is
  the moment to split, and it would be a new decision, not this one.

## 8. What this actually costs — and why it is not weekend work

**Stated plainly, as asked, rather than compressed to fit the calendar.**

| Stage | Realistic | Why it cannot be squeezed |
|---|---|---|
| Design review and acceptance | 0.5 day | Owner decision; §5.1's scoping limitation deserves a real read, not a skim. |
| Migration + model + rollback + **rehearsal** | 1–2 days | Tier 1. `CHANGE-PROCEDURE.md` requires a rehearsed rollback for a migration. The rehearsal database is one command, but a new table with three enums and four indexes needs its down-path actually exercised. |
| Endpoint + ingest service + tests | 1–2 days | Mirrors an existing pattern, which helps; batch handling and idempotency are new and are where the bugs live. |
| Hook push path: buffering, drop policy, tests | 1–2 days | §5.4. Detached, bounded, non-blocking, and must not be able to fail a request. This is the part most likely to be got wrong under time pressure, and the failure mode is adding latency to the request path — the exact harm the capability exists to detect. |
| Console view + tests | 1–2 days | Includes the percentile queries and their own correctness tests. |
| Credential provisioning + Secret plumbing | 0.5 day | Owner-gated, serialized, cannot be parallelised. |
| Release, restart, live verification | 0.5 day | Three sequenced gates (§5.5). |
| **Total** | **6–10 working days** | |

**This weekend is not enough time, and the honest recommendation is not to
try.** What would have to be cut to fit two days is precisely the part that
should not be: the migration rehearsal, the buffering correctness, and the
credential's provisioning discipline. A rushed version of this change would add
an unbounded table to a store with no purge path, behind a credential scoped
wider than anyone would choose, with a push path that can add latency to every
request — in service of measuring latency.

**What should happen this weekend instead:** CHG-2026-041's stdout bridge, which
is merged-ready, adds no schema, no credential and no release, and yields both
missing figures in a parseable form. It is not durable and does not pretend to
be. It is enough to make the switch-on measurable, which is the actual
requirement for this weekend. This ADR then proceeds on its own timeline with
its rehearsal intact.

## 9. Risks

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Unbounded growth in a store with no purge path (P0-11) | **High** — it is the default | High | §3.5: add to the retention job's scope before shipping, or ship with a stated shorter retention. Health rows carry no prompt content, so aggressive purging is safe here. |
| The push path adds latency to every request | Medium if rushed | High | §5.4: detached, bounded buffer, never awaited. Tested for it explicitly. |
| Credential scoped wider than intended | **Certain** — the auth model allows nothing tighter | Medium | §5.1: dedicated key, `expiresAt`, project scope, identifying note. Named as an open limitation, not presented as solved. |
| Health rows treated as decision evidence | Low | Medium | Separate table, separate view, separate enum. §3.1 records why. |
| Data produced but never looked at | **Medium** | Medium | §4.3 is explicit that there is no alerting. A readiness claim resting on this should say "reviewed", not "monitored". |
| Migration rollback untested under time pressure | Low if §8 is respected | High | Do not compress §8. |

## 10. Open questions for the owner

1. **Retention for this table**: add to PR #51's scope (which is itself gated on
   ADR-0004), or ship with a stated unbounded caveat and a shorter target?
2. **Alerting (§4.3)**: worker-evaluated thresholds, export to customer
   monitoring, or accept "reviewed not monitored" for now?
3. **The narrower access level (§5.1)**: worth opening as its own change, or
   accept project scope for the foreseeable future and record it as a known
   limitation?
4. **Sequencing**: does this start after the guardrail switch-on (so the bridge
   data informs the schema), or in parallel? Starting after is cheaper and the
   bridge is designed to make that viable.
